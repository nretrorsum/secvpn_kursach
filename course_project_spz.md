> Дисципліна: Системне програмне забезпечення  
> Група: КІ-31, Львівська Політехніка

---

## Технічне завдання

**Завдання на курсовий проєкт** *"Розробка програми для забезпечення безпеки віддаленого доступу до комп'ютера"*

**Мета проєкту:** розробити програму, що забезпечує безпечний віддалений доступ до комп'ютерної системи. Програма повинна організовувати захищений мережевий тунель між клієнтом і сервером на основі протоколу TLS 1.3 з взаємною автентифікацією сторін (mTLS) та шифруванням передаваних даних алгоритмом AES-256-GCM, протидіючи типовим мережевим атакам.

**Вимоги до курсового проєкту:**

1. Програма повинна працювати під управлінням операційних систем macOS 13+, а також мати сумісність з Linux (Ubuntu 22.04+). Підтримка Windows є бажаною, але необов'язковою.
2. Низькорівнева криптографічна підсистема повинна бути реалізована у вигляді динамічної бібліотеки (`.so` / `.dylib`) мовою програмування C/C++ з використанням бібліотеки OpenSSL. Клієнтський та серверний компоненти розробляються мовою Go з інтеграцією C/C++-бібліотеки через CGo-інтерфейс.
3. Програма повинна мати консольний інтерфейс командного рядка з підтримкою інтерактивного введення команд та відображення їх результатів у реальному часі.
4. Система повинна реалізовувати власну інфраструктуру відкритих ключів (PKI): генерацію кореневого центру сертифікації (Root CA), видачу серверного та клієнтських сертифікатів формату X.509, а також їх валідацію при кожному підключенні.
5. Програма повинна забезпечувати взаємну автентифікацію учасників з'єднання (mTLS): підключення без валідного клієнтського сертифіката, виданого довіреним CA, повинно автоматично відхилятися сервером.
6. Серверний компонент повинен вести журнал сесій: фіксувати IP-адресу клієнта, Common Name сертифіката, час підключення та відключення, а також перелік виконаних команд.
7. Програма повинна реалізовувати захист від атаки грубою силою (Brute Force): обмеження кількості невдалих спроб підключення з однієї IP-адреси за одиницю часу (rate limiting) з тимчасовим блокуванням підозрілих адрес.
8. Програма повинна формувати звіт активних та завершених сесій, що містить інформацію про учасників з'єднань, їх сертифікати, тривалість сесій та виконані дії.

## Архітектура системи

### Стек технологій

| Шар | Технологія | Файл |
|-----|-----------|------|
| Криптографічна бібліотека | C/C++ + OpenSSL | `libsecvpn.so` / `libsecvpn.dylib` |
| Міст між мовами | CGo | `bridge.go` |
| Сервер | Go | `vpnd` |
| Клієнт | Go | `vpnctl` |

### Схема компонентів

```
[Клієнтська машина]                    [Серверна машина]
        │                                      │
   vpnctl (Go)                           vpnd (Go)
        │                                      │
   CGo bridge                            CGo bridge
        │                                      │
   libsecvpn (.dylib)    ←TLS 1.3/mTLS→  libsecvpn (.dylib)
   ┌─────────────┐                        ┌─────────────┐
   │ OpenSSL TLS │                        │ OpenSSL TLS │
   │ AES-256-GCM │                        │ AES-256-GCM │
   │ PKI / certs │                        │ PKI / certs │
   └─────────────┘                        └─────────────┘
        │                                      │
   macOS/Linux мережевий стек (TCP/IP)
```

### Що є чим

- **libsecvpn** — серце системи. Динамічна бібліотека C/C++, яка є **обгорткою навколо OpenSSL**. Не реалізує TLS з нуля — викликає `SSL_CTX_new`, `SSL_accept`, `SSL_read/write` тощо і надає зручне API для Go.
- **CGo bridge** — шар склею між Go і C. Дозволяє Go-коду викликати функції з `libsecvpn.h`.
- **vpnd** — Go-демон, слухає TCP-порт, для кожного підключення запускає goroutine, виконує команди, логує сесії.
- **vpnctl** — Go-клієнт, підключається до vpnd, надає інтерактивний shell.

## CGo bridge

```go
// bridge.go
package secvpn

/*
#cgo LDFLAGS: -L./lib -lsecvpn -lssl -lcrypto
#include "libsecvpn.h"
*/
import "C"
import "unsafe"

func ServerConnect(ctx *C.secvpn_ctx_t, fd int) *C.secvpn_conn_t {
    return C.secvpn_accept(ctx, C.int(fd))
}

func Read(conn *C.secvpn_conn_t, buf []byte) int {
    return int(C.secvpn_read(conn,
        (*C.uint8_t)(unsafe.Pointer(&buf[0])),
        C.int(len(buf))))
}
```

> **Важливо про CGo і пам'ять:** Go і C мають різні системи управління пам'яттю (GC vs manual). Передавати Go-вказівники в C можна лише якщо вони не містять інших Go-вказівників всередині. Це потрібно описати в записці.

## Логіка vpnd (сервер)

```
1. Ініціалізувати TLS-контекст через CGo (завантажити server.crt, server.key, ca.crt)
2. tcp.Listen(":8443")
3. Для кожного вхідного з'єднання → goroutine:
   a. secvpn_accept()  → TLS handshake + mTLS перевірка сертифіката клієнта
   b. Логувати: peer CN, IP, час підключення
   c. Перевірити rate limiting (чи не заблокований IP)
   d. Цикл: читати команду → виконати os/exec → повернути stdout/stderr
   e. При закритті: логувати час відключення
```

## Логіка vpnctl (клієнт)

```
1. Ініціалізувати TLS-контекст (завантажити client.crt, client.key, ca.crt)
2. tcp.Dial(host + ":8443")
3. secvpn_connect() → TLS handshake
4. Інтерактивний цикл:
   > ввести команду → зашифрувати → відправити серверу
   ← отримати відповідь → розшифрувати → вивести на екран
```

## Теорія: TLS 1.3

TLS 1.3 (RFC 8446, 2018) — транспортний протокол безпеки. Працює між TCP і застосунком.

### Handshake (1-RTT)

```
Клієнт                                        Сервер
  │─── ClientHello + ecdh_pub_key_A ──────────→│
  │←── ServerHello + ecdh_pub_key_B ───────────│
  │    [обидва обчислюють shared_secret]        │
  │←── Certificate + CertificateVerify [🔒] ───│
  │─── Certificate (клієнта) + Verify [🔒] ───→│  ← це mTLS
  │←── Finished [🔒] ──────────────────────────│
  │─── Finished [🔒] ──────────────────────────→│
  │════ Application Data [AES-256-GCM 🔒] ══════│
```

**Переваги TLS 1.3 над 1.2:**
- Лише 1 тур до початку передачі даних (1-RTT замість 2-RTT)
- Виключені застарілі алгоритми (RC4, DES, RSA Key Exchange, MD5)
- Forward Secrecy обов'язковий (ECDHE завжди)
- Менша поверхня атаки

---

## Теорія: ECDHE — обмін ключами

ECDHE (Elliptic Curve Diffie-Hellman Ephemeral) дозволяє двом сторонам отримати спільний секрет, не передаючи його по мережі.

```
Клієнт:  генерує privA (секрет)
         pubA = privA × G  (публічний, відправляє)

Сервер:  генерує privB (секрет)
         pubB = privB × G  (публічний, відправляє)

Обидва обчислюють:
  privA × pubB = privB × pubA = shared_secret
```

**Ephemeral** = ключі генеруються заново для кожної сесії і знищуються після закриття. Навіть якщо зловмисник запише трафік і потім зламає довгостроковий ключ — старі сесії розшифрувати неможливо. Це **Forward Secrecy**.

Зломити ECDHE = розв'язати задачу дискретного логарифму на еліптичній кривій (ECDLP) — обчислювально нереально при 256-бітному ключі.

## Теорія: PKI та сертифікати X.509

```
Root CA (ca.crt + ca.key)
    │  підписує своїм приватним ключем
    ├── server.crt  (сертифікат сервера)
    └── client.crt  (сертифікат клієнта)
```

**Сертифікат X.509** — файл, що містить:
- Публічний ключ власника
- Метадані (CN, термін дії, для кого виданий)
- Цифровий підпис CA

**Перевірка:** при отриманні сертифіката перевіряється підпис через публічний ключ CA (`ca.crt`). Підробити сертифікат без `ca.key` — неможливо.

**mTLS (Mutual TLS)** — розширення стандартного TLS: сервер також вимагає і перевіряє сертифікат від клієнта. Підключитися може лише той, кому CA видав валідний клієнтський сертифікат.

---

## Теорія: AES-256-GCM

Симетричний алгоритм автентифікованого шифрування (AEAD).

- **AES-CTR** — шифрує блоки по 128 біт у режимі лічильника
- **GHASH** — рахує MAC (код автентифікації повідомлення)

```
Encrypt(key, nonce, plaintext, aad) → ciphertext + tag(16 байт)
Decrypt(key, nonce, ciphertext, tag, aad) → plaintext або FAIL
```

- Якщо хтось змінить хоч один біт у зашифрованому пакеті → GHASH не зійдеться → пакет відкинутий
- `nonce` — унікальний для кожного пакету (лічильник сесії). Повторення nonce = катастрофа для безпеки
- Схвалений NIST для рівня SECRET

---

## Теорія: загрози та захист

| Загроза | Суть | Захист у системі |
|---------|------|-----------------|
| MITM (Man-in-the-Middle) | Перехоплення та підміна трафіку | mTLS — обидві сторони перевіряють сертифікати CA |
| Replay Attack | Повторне відтворення перехоплених пакетів | ECDHE (новий ключ щосесії) + nonce в AES-GCM |
| Brute Force | Перебір паролів / ключів | Rate limiting, 256-бітні ключі (NIST), блокування IP |
| Command Injection | Впровадження шкідливого коду через команди | Валідація вводу, мінімальні привілеї (PoLP) |

---

## Де живе шифрування (важливо!)

```
[ vpnd / vpnctl ]        ← user space (твій застосунок)
       ↕
[ libsecvpn / OpenSSL ]  ← user space (шифрування тут!)
       ↕ зашифровані байти
[ TCP / IP стек ядра ]   ← kernel space (просто переносить байти)
       ↕
[ Мережева карта ]       ← hardware
```

**TCP не шифрує нічого.** Він лише транспортує байти. Шифрування відбувається у user space через OpenSSL **до** потрапляння даних у TCP.

Справжні VPN (WireGuard) працюють у **kernel space** через kernel module — тому швидші. Але це на порядок складніше і для курсової не потрібно.

**Ти не пишеш свій TLS** — ти пишеш **обгортку навколо OpenSSL**. OpenSSL реалізує TLS 1.3, ECDHE, AES-256-GCM. Твій код організовує їх правильне використання, будує PKI, захищає від атак. Це і є системне програмування.

## Фраза для захисту

> "Клієнт і сервер встановлюють TCP-з'єднання, потім за допомогою бібліотеки libsecvpn проводять TLS 1.3 рукостискання з взаємним обміном ECDH-ключами та перевіркою сертифікатів X.509, після чого весь трафік команд шифрується AES-256-GCM і недоступний для перехоплення або підміни. Шифрування реалізоване у user space засобами libsecvpn на базі OpenSSL — по мережі передаються вже зашифровані байти, а TCP виступає лише транспортом."
